## 2. Architecture

```
Browser ──┐
          │  MediaPipe Tasks Vision @12fps (face, multi-face, pose, gaze)  ← local, no network
          │  Web Audio (noise), lockdown.js (fullscreen/blur/screen-share)
          ▼
    nginx proxy :80 ─┬─ /api/*  → core-api :8000 ─┬─ postgres  (data-net)
                     │                             ├─ ai-worker :8010  (ai-net)
                     └─ /*      → frontend :8080   └─ /var/run/docker.sock → per-test-case sandbox
```

Three design decisions stand out as correct and worth preserving:

**Server-authoritative lockdown.** Strike counts derive from persisted `ProctorEvent` rows, not client state, so a page refresh or a `localStorage` wipe cannot reset them. Debouncing folds a burst (one Alt-Tab fires blur + visibilitychange + fullscreenchange) into a single strike. `lockdown_service.py` is honest in its own docstring about what it can't stop (OS screenshots, a second device).

**One access-control function, three call sites.** `organization_service.can_student_access_exam` is reused — not reimplemented — by the exam list endpoint, the exam detail endpoint, and `attempt_service.start_attempt`. The classic failure in this kind of system is filtering a list correctly while leaving the direct-ID endpoint open; sharing one function closes that by construction.

**The AI worker runs the same module, not a port of it.** `ai_worker/main.py` imports `app.ai.face_service` directly rather than reimplementing inference, which is the only way to guarantee that embeddings computed on either path are bit-identical and comparable against the same `FACE_MATCH_TOLERANCE`.

## 4. Findings

### 4.1 🔴 Critical — two enum values will crash against real PostgreSQL

The enum columns use **native Postgres enum types**, so every Python enum member needs a matching `ALTER TYPE ... ADD VALUE` in a migration before it can be inserted. I extracted every `ALTER TYPE` statement across all 15 migrations and diffed the result against `app/models/enums.py`. Two members have no migration:

| Member | Enum type | Reachable from |
|---|---|---|
| `QuestionType.MULTI_SELECT` (`"multi_select"`) | `questiontype` | Examiner authoring a select-all-that-apply question |
| `EventType.SCREEN_SHARE_STOPPED` (`"screen_share_stopped"`) | `eventtype` | `lockdown.js:147` → `/proctoring/lockdown/strike`, whitelisted in the endpoint's own regex and in `lockdown_service.STRIKE_EVENT_TYPES` |

Migration `0004` creates `questiontype` with exactly `("mcq", "coding")`; `0011` adds the multi-select *column* but never the enum *value*. Migration `0003`/`0005`/`0007` add six, two, and one `eventtype` values respectively — `screen_share_stopped` is in none of them.

The whole test suite passes because `conftest.py` runs on SQLite via `Base.metadata.create_all()`, which always reflects the current Python enum regardless of migration history. Against real Postgres, the first insert of either value fails with `InvalidTextRepresentation` — and for `screen_share_stopped`, that's a 500 in the middle of a live proctored exam.

**Fix:** one migration `0016` with `ALTER TYPE questiontype ADD VALUE IF NOT EXISTS 'multi_select'` and the same for `eventtype`/`screen_share_stopped`. Follow the existing pattern in `0003_add_advanced_proctoring_event_types.py` (each `ADD VALUE` outside the enclosing transaction).

### 4.2 🔴 Critical — `git init` was run, but nothing has ever been committed

`git log` returns *"your current branch 'main' does not have any commits yet."* All ten top-level entries are untracked. Half-fixed is functionally unfixed here: there is still no history to review, no branch to work safely on, and nothing to revert to. The `.gitignore` is already correct and thorough (`.env` excluded, `!.env.example` negated back in, model weights and uploads excluded). One `git add -A && git commit` away.

### 4.3 🟠 High — the whole API is enumerable outside the proxy in the shipped production compose

Two things compound:

- `app/main.py` constructs `FastAPI(...)` with no `docs_url=None` / `openapi_url=None`, so `/docs`, `/redoc`, and `/openapi.json` are public and unauthenticated in every environment.
- `docker-compose.yml` publishes `core-api` on `"8000:8000"` — commented as "purely for local development convenience" — while `deploy/nginx/nginx.conf`'s own header states that "nothing else in this compose stack publishes a port to the host."

With `ENVIRONMENT=production` in the shipped `.env`, `docker compose up` on a public host exposes all 91 endpoints and their schemas directly, bypassing the proxy — and with it the proxy's `client_max_body_size 12m`, which is currently the only real cap on request size (see 4.5).

**Fix:** gate `docs_url`/`openapi_url` on `settings.is_production`, and drop or comment out the `8000:8000` mapping in the default compose file.

### 4.4 🟠 High — CPU-expensive AI endpoints have no rate limit

`rate_limit()` is applied to exactly two routes: `/auth/login` and `/auth/register`. These four are not:

| Endpoint | Cost per call |
|---|---|
| `POST /proctoring/face/verify` | ArcFace inference, up to 7 MB base64 in |
| `POST /proctoring/id-card/verify` | EasyOCR (PyTorch), up to 7 MB in |
| `POST /proctoring/objects/detect` | YOLO11s, up to 7 MB in |
| `POST /proctoring/pose/check` | MediaPipe, up to 7 MB in |

Every one requires only `require_student` — any enrolled candidate, or anyone with a leaked student token, can loop these and starve every concurrent exam of CPU. The existing `rate_limit` dependency is a per-route drop-in; the only wrinkle is that it keys on client IP, which is the wrong key here — a per-user bucket would be the better fit for authenticated endpoints.

### 4.5 🟠 High — batch event bodies are capped, but only to ~350 MB

`ProctorEventBatchCreate` now caps at `max_length=50` events and `screenshot_base64` at `max_length=7_000_000` (a real improvement since the last review). But those multiply: 50 × 7 MB ≈ **350 MB** of JSON parsed into the API process's memory before validation rejects anything. The nginx `client_max_body_size 12m` is what actually holds the line today — and per 4.3, the published port 8000 goes around it. An app-level total-body cap (or dropping `max_length` on the per-event screenshot when it appears in a batch) would make this defense-in-depth rather than proxy-dependent.

### 4.6 🟠 High — no retention or deletion path for biometric data

The system stores, indefinitely: ArcFace face embeddings, registration face photos, ID-card images, and violation screenshots. Grepping for `delete`/`purge`/`retention`/`erase` across services and routes turns up exam, question, and examiner deletion — and nothing at all for biometrics. `organizations.py:74` explicitly (and correctly) notes that removing a student from a cohort must *not* erase their assessment record, which is right for scores but leaves face data with no lifecycle at all.

For a product processing student biometrics this is the finding most likely to become a legal problem rather than a technical one. Minimum viable fix: an admin-triggered `DELETE /users/{id}/biometrics` that clears the embedding and unlinks the stored images, plus a documented retention window.

### 4.7 🟡 Medium — no Subresource Integrity, and the app HTML has no CSP

`frontend/index.html` loads five third-party resources from `cdnjs.cloudflare.com` (Chart.js 4.4.4, CodeMirror 5.65.16 core + CSS + two modes) with no `integrity`/`crossorigin` attributes, and `faceMesh.js` pulls MediaPipe Tasks Vision from `cdn.jsdelivr.net` at runtime. A CDN compromise executes arbitrary JS inside the exam page.

Compounding it: the strict `Content-Security-Policy: default-src 'none'` in `app/main.py` applies only to **API responses**. `frontend/nginx.conf` — which serves the actual HTML — emits no security headers at all, so the page that handles camera frames, exam content, and the JWT has no CSP, no `X-Frame-Options`, and no `Referrer-Policy`.

**Fix:** add `integrity=` hashes to the five static tags, and a `add_header Content-Security-Policy ...` block to `frontend/nginx.conf` allowlisting the two CDNs.

### 4.8 🟡 Medium — `python-jose` 3.3.0 (CVE-2024-33664) still in place

The `requirements.txt` comment is unusually honest about this — it correctly identifies that CVE-2024-33664 (JWE decompression bomb) *is* reachable from `jwt.decode` on an attacker-supplied bearer token, that CVE-2024-33663 is not on an HS256-only config, and that migrating to PyJWT is the durable fix. It's been triaged but not actioned. The actual change is small: `app/core/security.py` is 30 lines, and `jose.jwt.encode/decode` → `jwt.encode/decode` is close to a rename, with `JWTError` → `PyJWTError`.

### 4.9 🟡 Medium — the seed admin credential is public and on by default

`AUTO_SEED_ADMIN` defaults to `true` in `entrypoint.sh`, `.env.example`, *and* the live `.env`, and seeds `admin@examproctor.com` / `Admin@12345` on every boot. The credential is printed in the README and in `.env.example`. The moment this repo is public — which, given 4.2, is presumably the near-term plan — every deployment that never flipped the flag has a known admin login. Either default the flag to `false`, or force a password change on first login.

### 4.10 🟡 Medium — the production secrets gate is inert on the bare-metal path

`config.py::_validate_secrets` is well-designed: hard failure in production, warning locally. But `backend/.env` has no `ENVIRONMENT` key at all, so running the backend directly (README §3.2, the non-Docker path) resolves it to `"development"` and downgrades every check to a log warning. The Docker path is fine — root `.env` sets `ENVIRONMENT=production` and a real 86-character key. This is a partial fix since the last review; the remaining gap is the documented non-Docker deployment path.

### 4.11 🟡 Medium — documentation drift

| Claim | Reality |
|---|---|
| README §8: `GET /api/v1/attempts/{attempt_id}/certificate/pdf` | No route or `pdf_service` function contains "certificate". Only `/result/pdf` exists (`build_result_report`) |
| README: `python tools/liveness_probe.py` | `tools/` does not exist (flagged in `CODEBASE_REVIEW.md`, still open) |

### 4.12 🟢 Low — code and bundle odds and ends

- **Dead code:** `exam_repository.list_published_exams` (superseded by `organization_service.list_accessible_published_exams`, zero callers) and `schemas/attempt.py::AttemptSummaryOut` (zero references anywhere). Both safe to delete.
- **Single 522 KB bundle.** No code splitting, so a candidate on exam-day bandwidth downloads the entire admin dashboard, examiner dashboard, and marketing site before the exam renders. A `React.lazy` split on the three dashboard route groups is the highest-value 20-line change in the frontend.
- **Two very large page files:** `Exam.jsx` (2,236 lines) and `ExaminerDashboard.jsx` (1,948). Not wrong, but they're the two files where a future bug will be hardest to isolate.
- **`aep_` localStorage prefix and `@examproctor.com` seed domain** are pre-rename leftovers. Both documented as deliberate legacy-compat choices; cosmetic.

## 5. What's already right (don't touch)

- **Layering discipline.** ~40 backend modules, no API→repository shortcut, no service reaching into another's tables.
- **The code sandbox.** Base64 argv passing (never a shell string, never disk), output capped *inside* the container because the host's `capture_output` buffer is unbounded, a `BoundedSemaphore` on concurrent runs, and honest fail-closed behavior when `docker` isn't reachable. This is the strongest single module in the project.
- **Health check split.** Liveness is deliberately dependency-free so a DB blip doesn't trigger a restart storm; readiness checks the DB so the LB drains instead. Getting this distinction right is rarer than it should be.
- **Request-ID correlation** echoed in the header *and* the error body, so a user can read it off an error screen.
- **`FACE_MATCH_TOLERANCE = 0.38`** with the reasoning written down — that a false accept (someone else sits the exam) is categorically worse than a false reject (retake the capture).
- **Zero TODO/FIXME markers** across 24,000 lines.
- **Network segmentation** in compose: four networks, postgres reachable only from core-api, ai-worker only on `ai-net`.
