# Merit.Ai — Full Codebase and Structure Review

Scope: every backend source file (models, schemas, Alembic migrations, repositories, services, API routes, core config/security, AI modules, utility scripts), every frontend source file (pages, components, lib modules, styling and build config), both README files, and the top-level project layout. This was a read-only review — nothing in the codebase was changed while producing it. Where a finding could be checked mechanically (an enum's members against its migration history, a claimed statistic against the code it describes, whether a symbol has any callers), it was checked rather than assumed.

The headline result is that this is an unusually well-built and well-documented codebase for its scale. The architecture is consistently layered (API routes call services, services call repositories, repositories touch the database and nothing else), the AI proctoring and code-sandboxing subsystems are written with real attention to failure modes, and a large fraction of the comments explain a past incident or a rejected alternative rather than restating the line below them. The findings below are the exceptions to that pattern, plus one structural issue — the complete absence of version control — that turned an otherwise-routine cleanup step into a real loss of work.

## Missing files, and the case for version control

Five paths referenced by this project's own documentation and history are not present in the current working tree: the root `docker-compose.yml` that the README's setup instructions depend on, a `tools/` directory that the README tells developers to run (`python tools/liveness_probe.py`) to tune the anti-spoofing detector, a `deferred-docker/` directory that the original Docker code-execution files were archived into earlier in this project's life, `PRODUCTION_AUDIT.md` (a report produced for this project earlier in this same working session), and `backend/ai_worker/`, the optional standalone AI microservice directory. These were removed intentionally rather than lost, so there is nothing to recover here — but it does mean the README sections referencing them (the `docker compose up -d` setup step and the `tools/liveness_probe.py` tuning instructions, both cited again further down) are now pointing at paths that no longer exist and should either be updated or have those paths restored, whichever reflects where the project is actually headed.

Separately from those specific paths: this project has no `.git` directory anywhere in it and has never been placed under version control. That's worth fixing on its own merits regardless of the above — a repo of this size, with 280-plus backend tests and this much iteration already behind it, would benefit from the ability to review history, branch safely, and revert a bad change, none of which is available without it. `git init` plus the `.gitignore` you already have plus an initial commit is a low-effort, high-leverage next step.

## Project structure and naming

The top-level layout is clean and conventional: `backend/` (FastAPI) and `frontend/` (Vite/React) as siblings, each with its own README, dependency manifest, and config. Inside the backend, `app/` is cleanly divided into `models`, `schemas`, `repositories`, `services`, `api/v1`, `ai`, `core`, `database`, and `utils`, matching the layering the README describes and that the code actually follows. The one naming wrinkle worth flagging is that there are two directories named `models`: `backend/app/models/` holds the SQLAlchemy ORM classes, while `backend/models/` (gitignored, currently empty in this environment) is a cache directory for downloaded AI model weights. They serve unrelated purposes and sit at different depths, so collisions are unlikely in practice, but a newcomer skimming the tree could reasonably expect them to be the same thing.

Frontend naming is consistent throughout — PascalCase for every component and page file, camelCase for every function and hook, and a small, deliberately centralized set of shared modules (`lib/ui.js` for className recipes, `lib/api.js` for the fetch wrapper, `components/Icon.jsx` for the entire icon set) that stop the same pattern from being reinvented per-file. The `aep_` prefix used for every localStorage key (`aep_token`, `aep_theme`, `aep_role`, `aep_name`, `aep_user_id`) and the seed admin's `@examproctor.com` email look like leftover branding from before the product was renamed Merit.Ai, but both READMEs confirm this was a deliberate choice to stay compatible with a legacy vanilla-JS frontend that has since been fully retired. Nothing user-facing shows these strings, so this is cosmetic and safe to leave alone or clean up at your convenience — not something that needs attention on its own.

## Backend data layer: models, schemas, migrations

The SQLAlchemy models and Pydantic schemas are thorough and internally consistent, with deliberate redundant validation in a few places (for example, exam scheduling rules are checked once at the schema layer for a 422 and again at the service layer for a 400, because the service-layer check needs database state the schema can't see) that is explained rather than accidental.

The one concrete bug found in this layer is a real one: this project's enum columns use native PostgreSQL enum types, which means every Python enum member needs a matching `ALTER TYPE ... ADD VALUE IF NOT EXISTS` in an Alembic migration before it can actually be written to the database. Diffing the current members of `QuestionType` and `EventType` (in `backend/app/models/enums.py`) against every `ALTER TYPE` statement across all thirteen migrations shows two values with no corresponding migration: `QuestionType.MULTI_SELECT` and `EventType.SCREEN_SHARE_STOPPED` (verified again while finalizing this report — both names appear only inside migration docstrings/comments, never inside an actual `ALTER TYPE` statement). Both features work correctly today because the automated test suite runs against SQLite with `Base.metadata.create_all()`, which always reflects the current Python enum regardless of migration history — but the first time either value is actually inserted against a real Postgres database that has only run the existing migrations, that insert will fail with `InvalidTextRepresentation`. This is the same category of bug as the `attempt_resets` index issue fixed earlier in this project (migration 0012): invisible to tests, real against Postgres. A new migration adding the two missing `ALTER TYPE` statements resolves it.

Two small pieces of dead code live in this layer: `exam_repository.list_published_exams`, which has been superseded by `organization_service.list_accessible_published_exams` and has no remaining callers, and `schemas/attempt.py`'s `AttemptSummaryOut`, which is never referenced anywhere — the endpoints it looks like it was written for (`my_attempts`, `attempts_for_exam`) use a raw `list[dict]` response model instead. Neither causes any harm sitting in the codebase; both are safe to remove whenever convenient.

## Backend logic layer: repositories and services

The repository/service split is applied consistently everywhere, and the organization/tenancy access control is a good example of defense in depth done right: `organization_service.can_student_access_exam` is the single function that decides whether a student can see or start a given exam, and it is reused — not reimplemented — by the exam list endpoint, the exam detail endpoint, and `attempt_service.start_attempt`. That matters because the natural mistake in this kind of system is to filter a list correctly while leaving a direct-id endpoint open; sharing one function across all three closes that gap by construction rather than by remembering to check it three times.

The sandboxed code-execution service (`code_runner_service.py`) is the highest-risk component in the backend and is hardened appropriately: containers run with no network access, a read-only root filesystem with a size-capped tmpfs for `/tmp`, all capabilities dropped, `no-new-privileges`, a non-root user, per-run memory/CPU/process limits, output-size caps enforced on both sides of the container boundary, a bounded concurrency semaphore, and student code passed through argv as base64 rather than interpolated into a shell string. Nothing found here needs changing.

The one gap in this layer is a UX/product one rather than a bug: `Exam.instructions` is a real field, fully wired from the database model through the schema, the service, and the examiner-facing editing form (`ExamDetailsForm` in `ExaminerDashboard.jsx`), but it is never read anywhere in the student-facing pre-exam page — confirmed by checking every reference to `.instructions` in the frontend: all five live in `ExaminerDashboard.jsx`, none in `Exam.jsx`. `Exam.jsx`'s "Instructions & exam rules" section on the system-check screen is a fully hardcoded, generic list rather than pulling in the per-exam text an examiner actually wrote. An examiner who fills in custom instructions today has no way to know a student never sees them.

## Backend API, core, AI, and utils

`core/config.py` already does the right thing for its one existing secret: `_validate_secrets` hard-fails application startup in production if `SECRET_KEY` is still the placeholder value or shorter than 32 characters. `utils/seed.py` does not get the same treatment — it creates a default admin account (`admin@examproctor.com` / `Admin@12345`) with no analogous production-time check or warning, and that exact credential pair is printed in the project's own README. A production deployment that runs the seed script as documented and does not immediately change that password is exposed by a credential pair anyone with access to this repository already knows.

The two-tier AI proctoring design (an optional external `ai_worker` service when `AI_SERVICE_URL` is configured, falling back to the same models running in-process) is implemented so that both paths are genuinely interchangeable — same embedding space, same output contract — rather than the fallback being a lesser approximation. The liveness/anti-spoofing split (a trained model when present, blocking; a classical heuristic otherwise, advisory-only) is explained in-code as a direct response to a real false-positive incident rather than a hedge.

The public "request examiner access" flow has a copy problem worth fixing: the confirmation screen (`RequestAccess.jsx`'s success panel), the backend's own response message for that endpoint, and the marketing copy on the home page (`Home.jsx`'s "Institutions & Examiners" card) all tell the requester "you'll receive an email with your login credentials once an administrator approves your account." A full search of the backend for any email-sending capability — SMTP, SendGrid, a mail client, anything — turns up nothing (re-confirmed while finalizing this report). There is no automated email anywhere in this codebase. The actual mechanism, once an admin approves a request, is a one-time on-screen credentials panel (`CredentialsHandoff.jsx`) that the admin is expected to copy and send manually — which works well and is designed thoughtfully, but is not what three separate pieces of user-facing copy currently promise.

## Frontend pages and routing

Every page file was read in full. The overall quality bar matches the backend: extensive comments that explain *why* a particular defensive check exists (a race condition that used to happen, a browser quirk that used to break a specific flow), consistent use of the shared `lib/ui.js` className recipes so buttons and cards never drift between pages, and careful accessibility work throughout — a skip-to-content link on the home page, a real focus trap with keyboard cycling in the exam lockdown overlay, `aria-live` regions for status updates rather than color-only signaling.

`Exam.jsx`, at over 2,200 lines, is comfortably the largest and most complex file in the project — it owns the pre-exam system-check flow, the timer, the question navigator, three different question-type renderers, the submit confirmation, and the lockdown/submitting overlays. It is not disorganized despite its size (helper components are factored out at the bottom of the file, and the state management is heavily commented), but it is the one file in the project that would benefit from being split into smaller pieces if it grows further.

Login.jsx, Register.jsx, and RequestAccess.jsx each independently implement the same form-validation pattern — a `computeErrors` function, an `update`/`handleBlur` pair, and a `touched` state object gating when errors display. All three implementations are correct and well-commented, but the pattern is duplicated three times rather than extracted into one shared hook. This is a maintenance observation, not a bug: a future change to how validation timing works would need to be made in three places instead of one.

One inaccuracy worth a quick fix: the marketing home page's stats strip (`Home.jsx`) states outright, in its own comment, that "every figure here is checkable against the code rather than rounded up for effect," and lists "17" for "Violation Types Tracked." The `EventType` enum it's counting currently has twenty members; excluding `LOCKDOWN_TERMINATED` (which the same file's comment correctly identifies as an outcome rather than a detected behavior, matching the stated methodology) leaves nineteen, not seventeen — recounted directly from `backend/app/models/enums.py` while finalizing this report. The number was accurate before `noise_detected_loud` and `screen_share_stopped` were added later and simply never got updated. The strike-limit figure next to it ("3") is correct and matches `LOCKDOWN_STRIKE_LIMIT`.

## Frontend components and lib

The client-side security layer (`lib/lockdown.js` and `lib/proctoring.js`) is the most carefully engineered part of the frontend. Both files are explicit about the boundary between what they enforce (fullscreen, focus, clipboard, screen-share continuity) and what they can only detect and log (screenshots, external recording devices) — a distinction the marketing page repeats honestly rather than overselling. The strike/resume logic in `lockdown.js` in particular handles a long list of real race conditions (two concurrent resume attempts, a stale status check landing after a second breach, a resume racing the server's own termination) with comments that read like they were written immediately after debugging each one. The only cosmetic note here is that the devtools/print/save keyboard-shortcut blocker logs its violation under the `copy_paste_attempt` event type, for lack of a more specific one in the enum — a minor mislabeling in an examiner's violation log, not a functional issue.

`components/Icon.jsx` centralizes the entire icon set behind a single `name` prop and silently returns `null` for any name it doesn't recognize. That's a reasonable default, but it means a typo in an icon name anywhere in the app fails silently — nothing renders, and nothing warns during development that a typo happened.

Config files (`vite.config.js`, `tailwind.config.js`, `postcss.config.js`, `package.json`) are all minimal and clean. The one real gap is testing: `package.json` defines `dev`, `build`, and `preview` scripts and nothing else — no `lint` script and no test runner of any kind. This is a real asymmetry against the backend, which has 280-plus passing pytest tests covering the full exam workflow, access control, and the AI helper modules. Every frontend verification done during this project's development has been ad hoc (a one-off esbuild bundle check), which works but leaves no regression safety net for the frontend comparable to what the backend already has.

## Documentation versus what the code actually does

The root README is detailed and, for the sections it covers, accurate — the AI proctoring table, the coding-sandbox explanation, and the auto-save/recovery section all match the code precisely. Cross-checking it against the current tree surfaced the same missing-files issue from the top of this report from a different angle: the README's setup instructions tell a new developer to run `docker compose up -d` from a `docker-compose.yml` that no longer exists, and its AI tuning instructions reference `tools/liveness_probe.py`, which is also gone. Separately, its "Extending this project" section still lists "add a screenshot capture on face_mismatch/multiple_faces events" as a suggested future improvement, but `lib/proctoring.js` already attaches a captured frame to every violation it raises, including those two — that line item looks done and was likely just never crossed off.

The frontend's own README has drifted further: its "Structure" section predates `lib/lockdown.js`, `lib/eventLogger.js`, and several components that now exist and are actively used (`CredentialsHandoff`, `EmptyState`, `RosterManager`, `Tagline`, `LogoMark`), and doesn't mention the `RequestAccess.jsx` page at all. More broadly, neither README documents several features that are fully built and shipped: the public access-request/approval flow, multi-select questions, exam scheduling windows with the candidate-status categorization on the student dashboard, draft-exam deletion, the examiner's ability to reset a student's exam, or the screen-share requirement added to the lockdown system. None of this affects how the app runs — it only affects how easy the project is for someone new (including a future version of yourself) to orient in without reading every source file the way this review just did.

## Everything that's already right

It's worth being explicit about what does not need attention, since a long list of findings can otherwise read as more alarming than the codebase actually is. The layered architecture is followed without exception across roughly forty backend modules. Tenancy and access control are centralized rather than duplicated. The code-execution sandbox and the AI proctoring fallback design both show real threat-modeling. Security headers, CORS handling, rate limiting on auth endpoints, and the secrets-validation gate are all already in place. The 280-plus backend tests pass, and they cover the parts of the system — access boundaries, scoring, the AI helper contracts — that are hardest to get right and most valuable to protect with tests. The frontend's accessibility work and its honesty about what browser-based proctoring can and cannot enforce are both genuinely above the bar for a project at this stage.

## Summary of items worth acting on, roughly in order

The Postgres enum migration gap for `multi_select` and `screen_share_stopped` is the highest-priority item in this report, since it's the one thing that will cause an actual runtime error the first time either feature is hit in production — worth fixing before either sees real traffic against Postgres. Putting the project under git (`git init` plus an initial commit) is the next highest-leverage change, independent of any specific bug. The default-admin production safeguard, the "you'll receive an email" copy in three places, the missing `exam.instructions` display on the student precheck page, and updating the README's setup/tuning instructions to match the current `docker-compose.yml`/`tools/` situation are all real, concrete gaps worth a short follow-up pass. Everything else in this report — the stale marketing statistic, the two dead code symbols, the leftover old-brand strings in generated PDFs and the API title, the duplicated form-validation pattern, the missing frontend test tooling, and the rest of the README drift — is minor polish that can be picked up opportunistically without any urgency.
