# --- PyTorch, CPU build, pinned explicitly ------------------------------------
# Both easyocr (OCR) and ultralytics (the YOLO export path / runtime fallback)
# depend on torch. This block is what makes them resolve to the CPU wheels.
#
# It is NOT optional and it is NOT a micro-optimisation. The comment below used
# to claim easyocr "pulls in PyTorch (CPU build)" -- nothing enforced that, and
# it stopped being true: the plain `torch` wheel on PyPI for linux x86_64 IS
# the CUDA build, and current versions declare the whole NVIDIA runtime as hard
# dependencies. An unpinned `torch` therefore downloaded, in one docker build:
#
#     torch                526 MB      nvidia-cublas          423 MB
#     nvidia-cudnn-cu13    366 MB      nvidia-nccl-cu13       206 MB
#     triton               198 MB      nvidia-cusparselt      170 MB
#     nvidia-nvshmem        60 MB
#     ------------------------------------------------------------
#     ~1.95 GB of GPU libraries
#
# None of it can ever execute here. ArcFace runs through onnxruntime's
# CPUExecutionProvider, insightface is prepared with ctx_id=-1, and the compose
# stack requests no GPU device. The only effects were a ~2GB image and a build
# that failed outright on any connection that couldn't hold files.pythonhosted
# open long enough to stream 423 MB (a read timeout mid-cublas is exactly how
# this first surfaced).
#
# The `+cpu` local version identifier is the mechanism: those wheels exist only
# on PyTorch's own index, so the pin cannot be silently satisfied by the CUDA
# build on PyPI. Every other package still resolves from PyPI as normal.
--extra-index-url https://download.pytorch.org/whl/cpu
torch==2.2.2+cpu
torchvision==0.17.2+cpu
